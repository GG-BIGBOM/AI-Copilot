# 把笔从模型手里拿走

> 一个 Agent 架构决定：**幻觉率 12.5% → 0%，代价是调试变难。**
>
> 阅读时间约 8 分钟。被问「讲一个你做过的最难的技术决策」时，这就是答案。
> 原始台账在 [ARCHIVE.md 的 M7 / M10 两节](../ARCHIVE.md)，这里是把它讲清楚的版本。

---

## 一、症状：Agent 上线，准确率掉了 12 个点

产品是一个旺店通旗舰版 ERP 的知识库问答助手。M7 之前它是一条**直路**：
用户提问 → 检索 → 把材料和铁律一起交给模型 → 流式吐答案。
41 道评测题上，它是 100% / 幻觉 0%。

M7 把它改成 Agent（Pydantic AI）。理由很正当：要做多轮需求收集、要出实施方案、
要按问题类型路由。改完之后同一份题集：

|  | 直路（M7 之前） | Agent（M7） |
|---|---|---|
| 准确率 | **100%** | 87.8%（−12.2） |
| 幻觉率 | **0%** | 12.5%（+12.5） |

⚠️ **这 12.5% 不是"答得不够好"。** 这个产品的幻觉长这样：

> 「进入【设置】-【物流管理】-【面单模板】，点击"批量同步"。」

——那个路径在系统里不存在。用户照着点，点不到；而他会先怀疑自己看错了菜单，
再怀疑是不是版本不对，最后打电话给实施顾问。**一个编出来的配置步骤，
能让客户第二天的订单卡在仓库里。**

## 二、排查：12 个点收敛成四条，每一条都可修

翻 M7 的失败样本，那批错的成因收敛成四条：

| # | 成因 | 具体表现 |
|---|---|---|
| 1 | **检索词漂移** | 直路拿用户原话（+ 改写）去检索；Agent 让模型自由写 `query`。「京东电子面单怎么配」被改写成「电子面单 模板 设置」，召回了得物那篇。命中率 100% → 93.9% |
| 2 | **材料串味** | 一轮里检索好几次，材料全堆进同一个上下文，模型拿第 B 次检索的材料回答 A 问题 |
| 3 | **拒答闸门变软** | 直路有两道**硬**闸门（召回为空直接返回、事后 `is_no_answer` 判定）；Agent 那边只剩一句 instruction。软闸门在 41 题上漏 12.5% |
| 4 | **换了 prompt** | 跑出 100% 的是 `qa.SYSTEM_PROMPT`，Agent 用的是另一份 `agent.INSTRUCTIONS` |

⭐ **四条的公因子只有一个：Agent 被允许拿原始材料自己写 ERP 答案。**

这一步是整段排查里最值钱的：四条看起来是四个独立的 bug，
可以一条一条修（改检索词来源、限制检索次数、加硬闸门、统一 prompt）。
**但那样修出来的是四条规则，而规则会松。**

## 三、决策：把工具分成两类

不修那四条，改结构：

|  | 返回给谁 | Agent 能不能改写 | 例子 |
|---|---|---|---|
| **普通工具** | 给 Agent 看的材料 | 能，Agent 自己组织话 | `current_time`、`save_requirement`、`generate_plan` |
| **终结工具** | **就是给用户的最终答案** | **不能，原样直通前端** | `answer_kb`、`whoami` |

```
用户提问
  └─ Agent（只做决策，输出只允许是工具调用）
       ├─ answer_kb(question)     ← 终结工具。内部 = 那条被量到 100% 的直路整条：
       │                             改写 → 检索 → system_prompt_for(mode) → 两道闸门
       │                             流式直通前端，Agent 不再复述
       ├─ current_time()          ← 普通工具
       ├─ save_requirement(...)   ┐
       ├─ generate_plan()         ├ 普通工具，多轮收集原样保留
       └─ export_excel()          ┘
```

`answer_kb` 里跑的是**那条被量到 100% 的链路，一个字不改**，只是被包了一层。于是：

- Agent 永远拿不到原始材料 → 上面四条成因**一次全消**
- 防幻觉规则回到**一份**（`qa.SYSTEM_PROMPT`），`agent.INSTRUCTIONS` 里只剩路由规则
- Agent 的职责收缩成**路由 + 多轮状态 + 编排**——正是它擅长、而直路做不了的

⭐ 一句话概括：**模型只能决定"要不要查"，不能决定"答什么"。**

### ⚠️ 边界必须是结构性的，不能靠 instruction

「现在几点了」这类让 Agent 自己答完全没问题。真正的风险在**边界**：
一旦允许它自由作答，「该查知识库还是自己答」就成了模型的判断题——
而这道题答错的样子，**恰好就是一条编出来的 ERP 配置**。

所以两道防线，缺一不可：

1. ERP 相关一律走 `answer_kb`，写死在 instructions —— 这是**软**的那道；
2. **越过工具直答检测** —— 本轮没调用任何终结工具、Agent 自己写了正文、
   且正文里出现界面路径特征（`【】`、`设置–`、「点击」、字段名），
   判为违规 → 记指标 + 兜底替换成拒答话术。这是**硬**的那道。

第 2 条同时是一个评测指标：**越过工具直答率，目标 0**，而且进了门禁。

## 四、结果

|  | M7 | M10 |
|---|---|---|
| 准确率 | 87.8% | **100%** |
| 幻觉率 | 12.5% | **0%** |

而且不是"调回去了"——是**结构上回不去**：Agent 再也看不到原始材料。

## 五、代价，说清楚

一个只说好处的架构决策不值得信。这个决定的代价有三条：

1. **模型看不到答案，调试变难。**
   答案在工具内部生成完再流出去，Agent 的对话历史里只有一句
   「已经把答案直接给用户了」。排查「这一轮为什么答成这样」时，
   要去看工具内部的 span，而不是看 Agent 的消息流。
   ⭐ 这也是后来做 OpenTelemetry span 树（W1.1）的直接动因之一。

2. **每轮多一次模型往返。**
   Agent 那一次只吐一个工具调用（几十 token），可以挂便宜快的模型
   （`agent_router_model` 可以和 `llm_model` 不同）。
   终结工具的正文流式直通，所以**首字延迟 ≈ 直路 + 一次 router 调用**，
   不是「等工具跑完再一次性吐」——这一点是主要的工程量所在。

3. **`answer_kb` 一轮只许调一次。**
   第二次调用会毁掉第一次的引用编号：那批 `[1][2]` 已经连着正文流给用户了，
   而 `citations` 只有一份。所以工具里第一件事是检查
   `deps.final_answer is not None`。

## 六、这段经历留下的三条判断

1. **看起来是四个 bug 的东西，往往是一个结构问题。**
   四条成因各自可修，但修出来的是四条会松的规则；改结构一次全消。

2. **防线要结构性的，不要 prompt 性的。**
   同一条规则写进 prompt 三次，模型照旧会违反；而"它压根看不到材料"
   这件事不需要它配合。
   ⚠️ 后来 M11 又验证了一次：主体约束那段 prompt 写了三轮、加到很长，
   私有库幻觉率仍然 16.7%；**把公共材料整块拿掉**之后立刻是 0。
   **材料在上下文里，模型就会用它。**

3. **架构决定要有一个能量它的指标，否则说不清对不对。**
   这次能说「12.5% → 0%」，靠的是 M7 之前就先扩了评测集——
   全 Agent 之后新增的失败模式（路由错、越过工具、多轮丢状态）
   在老题集上**一道都测不到**。⭐ 先扩题集，再改架构，顺序不能反。
